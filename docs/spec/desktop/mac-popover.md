# macOS Menu Bar Popover

## Status

The Popover is implemented as a genuine native `NSPanel` (`NSWindowStyleMask::NonactivatingPanel`), built directly with `objc2`/`objc2-app-kit` in [src-tauri/src/popover_panel.rs](../../../src-tauri/src/popover_panel.rs). **This is the current, only implementation** — the ordinary Tauri `WebviewWindow` this document described in earlier revisions no longer exists in the codebase (`install_popover_window`, `set_collection_behavior`/`set_popover_window_level`/`order_front_without_activating`/`invalidate_native_shadow`, `install_popover_dismiss_monitors`, and `position_popover_near_tray` were all removed from `src-tauri/src/main.rs`, along with the `"popover"` window label). It is retained in this document only as clearly marked history, for the reasoning it establishes, not as a description of anything still in the code.

The panel hosts the same `popover.html`/`popover.js` web UI unchanged, via `wry::WebViewBuilder::build_as_child` — the same WebKit embedding engine Tauri's own windows use, attached directly to the native panel `popover_panel.rs` builds, with a small hand-written `window.__TAURI__` shim (`BOOTSTRAP_JS` in that file) standing in for Tauri's own invoke/event plumbing, dispatching to the same underlying command implementations in `commands/mod.rs`. See [Native Panel](#native-panel), [Positioning](#positioning) and [Dismissal](#dismissal) below for the current mechanics.

This compiles, and the app starts and runs without crashing (`cargo build`/`cargo test`/`cargo clippy`/`cargo fmt --check` all clean; a debug run via `cargo run` stayed alive without panicking). What is **not** verified here: this environment has no attached display and no screen-capture/GUI-automation access, so the actual manual acceptance scenario — clicking the tray icon, checking the panel appears under it, checking it renders over a real Fullscreen Space, checking the first click lands, checking settings/theme sync from the Main Window, checking dismissal (including the repeat-click case fixed in [Dismissal](#dismissal)) — could not be exercised. In particular, the whole design leans on one assumption that could not be checked here: that a `wry`-hosted webview loaded from `tauri://localhost/popover.html` (registered via `WebViewBuilder::with_custom_protocol`) shares the same `WKWebsiteDataStore`-backed `localStorage` as the Main Window's own `tauri://localhost` webview, since both use the platform's default persistent data store under the same origin string. This needs a real-build check before the settings/theme cross-window sync criterion can be called confirmed.

## Intent

Add a second surface for macOS: a **Menu Bar Popover**, alongside the existing **Main Window**. Both exist at the same time and serve different jobs — the Popover is not a replacement for the Main Window, and there is no setting that switches between them. The Popover is the same application, the same backend logic, and the same three provider cards (Cursor, Claude, Codex), rendered through a smaller, simpler UI.

- Same data, same refresh logic, same settings model as the Main Window. Provider data comes from the application-wide structured-data cache, not from a separate Popover collection.
- Simpler layout than the Main Window: no Help entry point in the Popover.
- The three provider cards keep their content model from [provider-blocks.md](ui/provider-blocks.md) and [provider-block-content.md](ui/provider-block-content.md); the Popover only trims chrome around them, not the underlying data.

Two decisions are now fixed:

- **The Popover shows exactly what the Main Window cards show.** Same Limits/Subscription content and same values, not a reduced-information variant.
- **Display settings apply synchronously between Main Window and Popover.** Show limits / Show plan / Show source / Show update time ([settings.md#display](ui/settings.md#display)) reflect the same state in both surfaces. The synchronization mechanism is now implemented: `settings.js` emits a Tauri app event (`SETTINGS_CHANGED_EVENT`, `"settings-changed"`, defined in [constants.js](../../../frontend/modules/constants.js)) after every settings save, over `window.__TAURI__.event.emit`; `popover.js` listens for it via `window.__TAURI__.event.listen` and re-derives its own state from the (freshly reloaded) settings model. This also covers provider-visibility (Cursor/Claude/Codex) settings for which provider cards appear — see [Toolbar](#toolbar) for the details.

## Architecture

- **Application** — the whole app process.
- **Main Window** — the existing window described throughout [architecture.md](architecture.md) and [ui/](ui).
- **Menu Bar Popover** — a popover opened from the menu bar icon.

The Popover is not a separate application: same process, same [frontend modules](architecture.md#frontend-modules), same Tauri commands, same [settings](ui/settings.md), and the same application-wide structured-data cache as the Main Window. The cache holds one unchanged `StructuredSourceInfo` snapshot per provider after source-chain selection and account-field backfill. Each surface performs its own UI projection from that snapshot; neither stores a separate provider-data snapshot or rendered-card cache as a source of truth.

## Card Content

Popover cards drop the `Fix access`/`Retry` recovery buttons that appear on the Main Window's CLI-not-authorized, no-fresh-data, and generic-error Limits states (see [ui/provider-blocks.md](ui/provider-blocks.md) and [ui/problems.md](ui/problems.md)). Everything else in the card — Limits section, Subscription section, source line — is unchanged, per the "shows exactly what the Main Window cards show" decision above. Neither surface has per-card refresh controls; the shared update frequency is configured in the Main Window Settings page.

`renderProvider()` has a Popover-specific variation: `initProviders()`/`renderProvider()` take a `surface` parameter (`"main"` or `"popover"`), and `provider-rendering.js` emits the `Fix access`/`Retry` markup only when `surface === "main"`. `popover.js` passes `surface: "popover"`, so these actions are never rendered in the Popover.

## Toolbar

The panel's own chrome is a single fixed header strip above the scrolling card area — there is no separate footer strip and no View Tabs row (both dropped; see below):

```text
 AI Limits              [update all] [info] [gear]
 ─────────────────── cards ───────────────────
```

- **`AI Limits`** — opens the Main Window.
- **`[update all]`** — refreshes every visible provider. A hand-authored circular refresh glyph (`POPOVER_UPDATE_ALL_ICON_SVG` in [popover-toolbar.js](../../../frontend/modules/popover-toolbar.js)), drawn at the panel's own icon scale (15px, 1.5 stroke, `currentColor`) rather than reused from the Main Window's 18-20px/2.0 glyph builders.
- **`[info]`** — opens the Main Window, on the matching Help/info section.
- **`[gear]`** — opens the Main Window, on Settings.

The panel always shows every enabled provider's card, stacked top to bottom, with no way to filter down to a single provider — an earlier pass had a macOS segmented "View Tabs" control (`All`/`Codex`/`Claude`/`Cursor`) between a separate top strip and a separate footer strip; both were merged into the one header row above, and the tab control was removed outright. Providers still respect [provider visibility settings](ui/settings.md) (Cursor/Claude/Codex toggles) — that filtering happens in `providers.js` itself (`PROVIDER_IDS.filter(isProviderEnabled)`), not through a tab UI.

**Implemented.** `[info]`, `[gear]`, and `AI Limits` (see [Entry Points](#entry-points)) are real navigation, not stubs. `popover.js` defines `window.__openMainWindowHelp(chapterId?)`, `window.__openMainWindowSettings()`, and `window.__openMainApplication()` — the same three bridge-global names the earlier frontend-only phase left as documented no-ops — as thin wrappers around `window.__TAURI__.core.invoke(...)`, calling three Tauri commands in [src-tauri/src/commands/mod.rs](../../../src-tauri/src/commands/mod.rs):

- `open_main_window_help(chapter: Option<String>)` — shows+focuses `"main"`, then evals `window.__openHelpFromNative && window.__openHelpFromNative(<chapter or nothing>)` on it. Passing no argument at all (rather than an explicit `null`) when `chapter` is absent matters: `main.js`'s `openHelp(chapterId = DEFAULT_HELP_CHAPTER)` only applies its default for `undefined`, not `null`.
- `open_main_window_settings()` — shows+focuses `"main"`, then evals `window.__openSettingsFromNative && window.__openSettingsFromNative()`.
- `open_main_window()` — shows+focuses `"main"`, no eval (just brings the window forward, for `AI Limits`).

All three mirror the pattern `handle_menu_event` already used for the native Help/Settings menu items (same eval calls, same `Option`-guarded `get_webview_window("main")` lookup, no-op rather than error if `"main"` doesn't exist), just triggered by a Popover click and an `invoke()` instead of a native menu event. Each also explicitly hides the Popover panel on macOS after focusing `"main"`, via `show_and_focus_main_window`'s call to `hide_popover_window` (which calls `popover_panel::hide()`) in [src-tauri/src/commands/mod.rs](../../../src-tauri/src/commands/mod.rs) — this is the only mechanism that hides the panel here; the panel raises no focus-loss event of its own to fall back on, since it is a native `NSPanel` outside Tauri's window-event system (see [Native Panel](#native-panel)). These commands are not macOS-`cfg`-gated themselves (the popover-hide step inside them is); calling them on another platform just shows/focuses `"main"`, which is harmless.

The header is built by [popover-toolbar.js](../../../frontend/modules/popover-toolbar.js) — `buildPopoverHeaderHtml()` — and shared verbatim with the `?showcase=popover` preview. It is mounted once and never rebuilt (`attachPopoverHeaderHandlers()` is called once, not on every settings change), since none of its four actions depend on provider-visibility state anymore.

## Cross-Window Sync

Each Tauri webview window runs its own JS context with its own module-scoped copy of `settings.js`'s `appSettings` and `theme.js`'s `appTheme`, so a change saved in the Main Window updates localStorage but not an already-open Popover. Two Tauri app events bridge that gap, both defined in [constants.js](../../../frontend/modules/constants.js) and both emitted only under Tauri (a plain-browser context has no other window to notify):

- `SETTINGS_CHANGED_EVENT` (`"settings-changed"`, payload `{ kind: "visibility" | "display" | "update-frequency" }`) — emitted by `settings.js` after every settings save. `popover.js` listens, calls `reloadAppSettings()`, then re-renders the cards already mounted in the Popover from its local presentation cache. It synchronizes the four display toggles and the shared update frequency. Provider-visibility changes take effect when the Popover next initializes its provider list; a changed update frequency is applied to its refresh schedules immediately. Notifications and application auto-update remain Main-Window-only.
- `THEME_CHANGED_EVENT` (`"theme-changed"`) — emitted by `theme.js`'s `setManualTheme()`, i.e. the Main Window's "Dark theme" toggle. `popover.js` listens and calls the new `reloadAppTheme()`, which re-reads the theme storage key into this window's `appTheme` and re-applies `data-theme`. Kept separate from the settings event because the theme lives in its own storage key and its own module, and reacting to it means re-applying an attribute rather than re-rendering anything. *System* theme changes need no event at all: every window observes the `prefers-color-scheme` media query itself, which already worked.
- `PROVIDER_UPDATED_EVENT` (`"provider-updated"`) — one of three events emitted by the Rust backend rather than a frontend module, right after a successful actual collection updates the shared structured-data cache (`src-tauri/src/commands/collect.rs`; see [frontend-state.md](ui/frontend-state.md#shared-structured-data-cache)). `providers.js` listens (in `initProviders`, shared by both `main.js` and `popover.js`) and applies the payload straight to its own mounted card and refresh schedule, without calling `get_single_provider_limits` itself. This is what makes a collection started in one surface show up in the other without a second collection.
- `PROVIDER_REFRESH_STARTED_EVENT` (`"provider-refresh-started"`, payload `{ id }`) — emitted right as an actual collection begins, before the source chain runs. `providers.js` listens and marks that provider's card busy (`is-refreshing`) in every open surface, so the refresh animation for a card started in one surface plays in the other too, without either surface starting a second collection.
- `PROVIDER_REFRESH_FAILED_EVENT` (`"provider-refresh-failed"`, same `ProviderLimits` shape as `PROVIDER_UPDATED_EVENT`, built via `provider_error`) — emitted after a failed actual collection. A failed collection still does not touch the shared cache and still does not emit `PROVIDER_UPDATED_EVENT`; this is the event that lets a surface which did not start the collection show the same error state instead of silently keeping stale data, and it clears the busy state `PROVIDER_REFRESH_STARTED_EVENT` set.

The Popover has no settings UI of its own, so it is only ever a listener, never an emitter of `SETTINGS_CHANGED_EVENT`/`THEME_CHANGED_EVENT`, and `initSettings({})` is called there without `onChanged`/`onDisplayChanged` callbacks — those fire only for a change made *within* the same window, which cannot happen here. The three provider-refresh-lifecycle events are different: neither surface ever emits any of them itself — only the backend does, so both are listen-only for these too.

Unlike `SETTINGS_CHANGED_EVENT`/`THEME_CHANGED_EVENT`, the three provider-refresh-lifecycle events are forwarded to the Popover's non-Tauri-managed webview the same way (`popover_panel::install_event_forwarding` in `popover_panel.rs`, via `window.__popoverDispatchEvent`), but they originate from the backend's own `app.emit` rather than a frontend `window.__TAURI__.event.emit` call — the Main Window receives them through Tauri's ordinary event delivery for free, and only the Popover needs the explicit forwarding.

The card animation these three events drive — including the short flash played on a surface that applies a result without ever having seen the matching `provider-refresh-started` — is documented separately in [ui/refresh-animation.md](ui/refresh-animation.md).

## Entry Points

- **Menu bar icon** — a left click opens/closes the Popover; behaves as a toggle. It does not open or activate the Main Window. Implemented: a `TrayIcon` built in `install_tray_icon` ([src-tauri/src/main.rs](../../../src-tauri/src/main.rs)) handles left `TrayIconEvent::Click`, checking `popover_panel::is_visible()` and calling either `commands::hide_popover` or `popover_panel::show_near_tray` — see [Native Panel](#native-panel) — and never touches `"main"`. A right click opens a small context menu instead — see [Menu Bar Icon](#menu-bar-icon).
- **Dock icon** — visible only while the Main Window is visible; it is not an entry point after that window is closed.
- **`AI Limits` button inside the Popover's header** — opens the Main Window. Implemented: `popover.js`'s `window.__openMainApplication()` invokes the `open_main_window` Tauri command — see [Toolbar](#toolbar) for the full implementation writeup (shared with `[info]`/`[gear]`).

## Closing

- Closing the Popover hides only the Popover: `popover_panel::hide()` calls `panel.orderOut(None)` (never destroys the `NSPanel`) and tears down the dismiss monitors installed in [Dismissal](#dismissal). Every closing path below funnels through this one function (or the `hide_popover` command, which calls it) — see `commands::hide_popover_window` in [src-tauri/src/commands/mod.rs](../../../src-tauri/src/commands/mod.rs).
- The native, focus-independent dismiss mechanisms — click outside the panel, Escape, leaving the Space — are described in full in [Dismissal](#dismissal), including the tray-icon-click race those mechanisms have to account for.
- `popover.js`'s own `keydown` listener for Escape (invoking the `hide_popover` command) still exists, registered in the *capture* phase so it runs before providers.js's own bubbling Escape handler (which closes a card's open dropdown first, if one is open). It is largely redundant with the native Escape monitor in [Dismissal](#dismissal) — kept as a harmless fallback for the case where the panel did somehow become key and this in-page listener fires first. Outside Tauri (the page opened in a plain browser) `window.__TAURI__` is absent and the handler is a no-op.
- Navigating into the Main Window — `AI Limits`, `[info]`, `[gear]` (see [Toolbar](#toolbar), [Entry Points](#entry-points)) — also hides the Popover, via `show_and_focus_main_window` in `commands/mod.rs` calling `hide_popover_window` after showing/focusing `"main"`.
- Closing the Main Window hides it and removes the application icon from the Dock; the application keeps running (menu bar icon stays, Popover remains available). The Main Window can be reopened from the Popover or the menu-bar context menu. Implemented: `install_main_window_close_guard` intercepts the Main Window's `WindowEvent::CloseRequested` (red traffic light, Cmd+W), calls `api.prevent_close()`, leaves native fullscreen when necessary, then hides the window instead of letting it destroy. Leaving fullscreen first prevents macOS from retaining an empty AI Limits Space. Unrelated to the Popover panel and unchanged by the move to `NSPanel`.
- Quit fully terminates the application. Verified unaffected by the above: the native Quit menu item (`PredefinedMenuItem::quit` in `install_help_menu`) terminates the app directly through the OS's own menu action, not through a window's close-request path, so the close-guard never intercepts it.

## Launch Behavior

- **First launch** — open the Main Window. The configured window starts hidden; `launch::show_initial_window` atomically creates a marker in the app-data directory and shows the window only when that marker did not already exist. If the marker cannot be read or written, the Main Window opens so the application never starts with no accessible interface.
- **Normal manual launch after the first one** — do not open the Main Window automatically. The app is available through the menu bar icon; the user can explicitly open the Main Window from the Popover or the menu-bar context menu.
- **Autostart/login item** — launch in the background, show the menu bar icon, do not open the Main Window, do not open the Popover automatically. **N/A for this phase**: this app has no launch-at-login / autostart feature at all yet (no `tauri-plugin-autostart`, no LaunchAgent, no login-item registration anywhere in the codebase). This case is blocked on a launch-at-login feature that doesn't exist yet — implementing it is a separate, larger feature outside this phase's scope. Tracked in [Open Items](#open-items).

## UX Principle

- Menu Bar = quick access.
- Main Window = full work.
- The Popover opens only on an explicit user action (clicking the menu bar icon) — never automatically.

## Static Layout

Approach: build the Popover's real markup and styles first, previewed as static layout through the browser showcase, before any native tray/window logic exists. Once the layout is settled, the macOS-side logic (menu bar icon, popover open/close, window wiring) is built around it.

Two things now exist side by side:

- **The browser showcase preview** — [showcase.js](../../../frontend/modules/showcase.js) / [showcase.css](../../../frontend/styles/showcase.css), reachable via `?showcase=popover`, driven by mock `SHOWCASE_PROVIDERS` data.
- **The real, standalone Popover surface** — [popover.html](../../../frontend/popover.html) / [popover.js](../../../frontend/modules/popover.js), a second static entry point alongside [index.html](../../../frontend/index.html) / [main.js](../../../frontend/modules/main.js). It sits at the same level as the Main Window's entry point rather than living inside it, matching the "not a replacement, a different surface" framing in [Intent](#intent). It is reachable in the built app via the native `NSPanel` described in [Native Panel](#native-panel): `popover_panel::create_webview` in [src-tauri/src/popover_panel.rs](../../../src-tauri/src/popover_panel.rs) points its hosted webview at `tauri://localhost/popover.html`, served through a custom URL-scheme protocol handler backed by `AppHandle::asset_resolver()` — the same bundled-asset lookup the Main Window's own `"main"` webview resolves `index.html`/`frontendDist` through, just invoked directly rather than via `WebviewWindowBuilder`. It is real in every other sense too: it drives its own provider cards through the same [providers.js](../../../frontend/modules/providers.js) pipeline the Main Window uses (`initProviders`, `refreshEnabledProviders`, `initProviderIntervals`), against the real `get_single_provider_limits` Tauri command (dispatched through `popover_panel`'s own IPC bridge — see [Native Panel](#native-panel)) and the real settings/localStorage model — not mock data. Loaded in a plain browser (no `window.__TAURI__`), it shows the same "Tauri API is unavailable" status-line error the Main Window would show under the same condition; that's expected, not a bug.

Both surfaces share one module, [popover-toolbar.js](../../../frontend/modules/popover-toolbar.js), for all [Toolbar](#toolbar) markup and behavior (icons, header markup, header-button wiring), so they cannot drift apart. `showcase.js` no longer has its own inline copy of this logic.

Implemented, in both surfaces unless noted:

- `?showcase=popover` remains a fourth showcase mode alongside `macos`, `windows`, `linux`. It still does not render a duplicate or hand-copied mockup: it relocates the same live `#provider-list` element that `initProviders()` already mounts inside `.app` — the same real card markup, the same [`SHOWCASE_PROVIDERS`](../../../frontend/modules/showcase.js) mock data used by the other three platforms, the same interactivity — into the same `.popover-root` panel structure `popover.html` uses. `popover.html` mounts its own, separate `#provider-list` of the same shape, fed by the real pipeline instead.
- Unlike the `macos`/`windows`/`linux` showcase variants, the panel has no titlebar and no traffic lights — the Popover is not an OS window, so that chrome does not apply. It also has no resize handle; the OS-window screenshot resize behavior in [showcase.md](../../product/showcase.md) does not apply to it either.
- No Help entry point.
- The [Toolbar](#toolbar) is implemented: every enabled provider's card is always shown, stacked top to bottom — there is no tab control to filter them.
  - In `popover.html`, `[update all]` refreshes every enabled provider through the common collection path. The resulting shared structured snapshots are used by both surfaces; it does not initiate a separate Main Window collection.
  - `[info]` and `[gear]` are real cross-window navigation: they call two bridge globals, `window.__openMainWindowHelp(chapterId?)` and `window.__openMainWindowSettings()`, implemented via `window.__TAURI__.core.invoke` calls into the `open_main_window_help`/`open_main_window_settings` Tauri commands — see [Toolbar](#toolbar). A provider card's own "More details" link (shown on some data-error states) also routes through `window.__openMainWindowHelp`, via a small guard in [help.js](../../../frontend/modules/help.js)'s `openHelp()`: when no local Help view exists (true for `popover.js`, which never calls `initHelp`), it defers to that same bridge global instead of throwing.
  - The `AI Limits` header button calls a third bridge global, `window.__openMainApplication()`, same pattern, backed by the `open_main_window` command.
  - In the showcase preview the four actions are rendered-only, with no callbacks attached — the preview does not go through `popover.js` at all. Tab switching does work there, since that behavior lives in the shared module.
- The `Fix access`/`Retry` half is implemented the other way: a `surface` render-time option on `initProviders()`/`renderProvider()` (see [Card Content](#card-content)), because unlike the dropdown these buttons only exist on data-error states that not every card reaches, so there is no single static selector to hide. A CSS rule (`.popover-root [data-open-help], .popover-root [data-manual-refresh] { display: none; }`, in [popover.css](../../../frontend/styles/popover.css)) still exists as a safety net, but only for the `?showcase=popover` preview, which relocates the Main Window's already-rendered `#provider-list` (built with `surface: "main"`) into `.popover-root` instead of re-rendering it — the real Popover never renders these elements in the first place.
- Which provider cards appear is determined when the Popover initializes its provider list: `providers.js` filters `PROVIDER_IDS` through `isProviderEnabled` before rendering, so a disabled provider's card does not appear. Changes to provider visibility while the Popover is already open apply when it next initializes its provider list; see [Cross-Window Sync](#cross-window-sync). The showcase preview always shows all three `SHOWCASE_PROVIDERS`, unconditionally "enabled" there.
- Stylesheets: `popover.html` links its own entry point, [frontend/popover.css](../../../frontend/popover.css), instead of the Main Window's `styles.css`. It pulls in only what this surface renders — tokens, the shared base, the provider cards, and the panel layer — leaving out the Main Window nav bar, the settings page, the help view, the update banner and the screenshot-showcase chrome, none of which exist here. The panel layer itself is [frontend/styles/popover.css](../../../frontend/styles/popover.css), imported last by both entry points so its scoped overrides win; it is a real file of its own rather than a section of `showcase.css`, so the shipped window no longer depends on the screenshot-mockup stylesheet. See [Visual Layer](#visual-layer).
- CSP: `popover.html` introduces no new script/style/resource origins, so it is covered by the same `app.security.csp` in `src-tauri/tauri.conf.json` as `index.html` without changes — `script-src 'self'`, `style-src 'self'`, no inline styles or scripts, only local ES module imports.

Native tray/panel logic now exists on top of this layout — see [src-tauri/src/main.rs](../../../src-tauri/src/main.rs) and [src-tauri/src/popover_panel.rs](../../../src-tauri/src/popover_panel.rs): a `TrayIcon` (`install_tray_icon`) toggles the native `NSPanel` (`popover_panel::show_near_tray`/`hide`), positioned near the clicked tray icon and dismissed by the native monitors in [Dismissal](#dismissal) — see [Native Panel](#native-panel) for the current mechanics. Dock-icon reactivation and Main Window close-to-hide are wired up too (see [Entry Points](#entry-points) and [Closing](#closing)). `[update all]`'s real behavior still stops at starting collections for this window's own cards (no cross-window refresh — this was never in scope); the other open surface's matching cards still animate and update through the shared `provider-refresh-started`/`provider-updated`/`provider-refresh-failed` events described in [Cross-Window Sync](#cross-window-sync), without starting a second collection there. `AI Limits`/`[info]`/`[gear]` call real implementations of the bridge globals, backed by Tauri commands in [src-tauri/src/commands/mod.rs](../../../src-tauri/src/commands/mod.rs) — see [Toolbar](#toolbar) for the full writeup.

## Visual Layer

The panel is styled to read as a macOS menu bar panel (Control Center, the Wi-Fi/Sound/Battery panels), not as a scaled-down Main Window. Everything below lives in [frontend/styles/popover.css](../../../frontend/styles/popover.css), scoped under `.popover-root` so none of it leaks into the Main Window.

**The panel owns no size of its own.** Width comes from the native window (`POPOVER_WIDTH` in [src-tauri/src/windows.rs](../../../src-tauri/src/windows.rs)) and the panel simply fills it at `width: 100%`, so that number lives in exactly one place; height is `100vh` for the same reason (see [Window Size](#window-size)). The one geometric constant the panel does restate is the corner radius — see below.

**No card inside the window.** An earlier pass drew a `.popover-surface` box with an 88%-opaque background, a 1px border and a CSS shadow, inset by a 10px body padding — which covered the native vibrancy almost entirely, leaving the blur visible only as a thin frame. There is no such box now: the webview paints no panel background, no panel border and no panel shadow. Content runs edge to edge with ~10px side padding and slightly more top/bottom, so the native material is what fills the panel. `.popover-root` carries `border-radius: 11px` and `overflow: hidden` — the same 11pt the native panel's `CALayer` is given (`POPOVER_CORNER_RADIUS` in `popover_panel.rs`, see [Native Panel](#native-panel)), so hover highlights and the footer hairline clip on the panel's own curve. The `--mix-popover-surface` token the old model needed is gone from `tokens.css`.

**Everything is an alpha overlay.** Nothing inside the panel paints an opaque color over the material: text is near-opaque black/white, surfaces are white- or black-alpha washes. The panel defines its own `--pop-*` variables and, in the same scope, re-points the app-wide tokens the shared card CSS reads (`--text`, `--text-muted`, `--surface`, `--meter-bg`, the font sizes) at them. The global palette is untouched.

**Typography.** The Main Window's `--font-family-base` leads with Inter, for which this repo ships no `@font-face` — it resolves to whatever the user happens to have installed. A system panel must be San Francisco, so the panel scope uses `-apple-system, BlinkMacSystemFont, system-ui, sans-serif` with `-webkit-font-smoothing: antialiased`. The scale is the system-panel one — 13px body, 11px secondary/captions, 15px ceiling for emphasis — against the Main Window's 13/14/15/20/22, and rows sit at ~20-22px rather than desktop-card spacing.

**Cards as Control Center tiles.** The card keeps its content model unchanged ([Card Content](#card-content)) and changes only its dressing and density. Dressing: no border, no shadow, a 9px radius, and a neutral white-alpha fill — deliberately *the same* fill for every provider. A system panel's modules are neutral and let color carry data (the meters), not identity; the provider is named by its own row heading, so the brand tint an earlier pass put behind each card (and the brand-tinted text tokens the shared card CSS derives) is flattened away here. Meters are 3px, fully rounded.

**Card density.** The Main Window's card layout is what made the panel read as a shrunken app window even after the chrome was fixed, so the tile re-lays the same data in system idioms. All of it is CSS scoped to `.popover-root`; the only change to shared markup is that `provider-rendering.js` now emits key-value text as `label` / `separator` / `value` spans instead of one flat string, which concatenates back to the exact same line in the Main Window.

- **Section heading rules are gone.** `——— LIMITS ———` / `——— PLAN ———` costs two lines per section and is the strongest desktop-card signal inside the tile. The two sections are then handled differently, because they carry different weight: the Limits heading is dropped entirely (its rows are self-describing — a period, a percentage and a meter), while the Subscription heading becomes the *left-hand key* of a key-value row with the plan lines as its right-hand value, costing no extra line at all.
- **Limit rows** are two lines instead of three: the period on the left, the value hard right, the reset time as secondary text between them, and the meter underneath. `.limit-top` is `display: contents` in this scope so its label/value spans join the row's grid directly and can be placed on either side of the reset time, which is a sibling element rather than one of its children.
- **Available credits / Available resets / Plan** are label-left, value-right menu rows, not `Label: value` run together in one column.
- One Main-Window behavior is switched off: `providers.js`'s `applySectionSlotAlignment` writes an inline `min-height` on each section so equal sections line up across side-by-side cards; in a single stacked column that only pads each card with dead space, so the panel overrides it (the one `!important` in the file — an inline style cannot be beaten otherwise — leaving the alignment logic itself untouched for the Main Window).

Measured against the `SHOWCASE_PROVIDERS` mock data, all three provider tiles together occupy ~400px of height, against ~1250px before this pass.

**Controls.** The view tabs are a segmented control (alpha track, raised pill for the selected segment, 12px medium, ~22px tall, 7px/6px radii). Icon buttons are 22x22 with no border or background at rest, a rounded alpha wash on hover and a denser one while pressed. The footer is a full-width hairline with a system-menu row under it, labeled "Open AI Limits" — system panels name the app they open ("Wi-Fi Settings…"), not "the application". Its hover is a neutral alpha wash rather than the system blue selection fill, which would fight the app's own warm/green accent palette.

**No web artifacts.** Text selection, drag-out, tap highlight and the pointer cursor are all off; `popover.js` cancels the `contextmenu` event so right-clicking gives no WebKit Reload/Inspect menu. Focus rings appear only for `:focus-visible` and are a quiet 1.5px inset ring, not base.css's 2px green `--focus` outline. Only the card area scrolls — the top bar and footer are fixed — with `overscroll-behavior: none` (no rubber-band) and a thin overlay scrollbar that is invisible until the pointer is over the list. When the list does overflow, its bottom edge is faded out with a mask so the row the footer hairline cuts through reads as "there is more below" rather than as a layout bug; the fade is toggled by `observePopoverScroll` (popover-toolbar.js, shared with the preview) and is absent whenever the content fits or the list is scrolled to its end.

## Window Size

The width is owned by the native side (`POPOVER_WIDTH`, 348 logical px) and never changes; the panel lays out against the same number.

The height is content-driven, the way system menu bar panels are, rather than a fixed size that is too tall for one provider card and too short for three failing ones. `popover.js` reports the height the panel wants through the `set_popover_height` command: the two fixed strips (top bar, footer) plus the natural height of the card list. It measures the card list, never `.popover-scroll` — that element is stretched to whatever height the window currently has, so measuring it would be circular and would pin the window at its first size forever. The report is driven by a `ResizeObserver` on the card list rather than hooked into each of the many things that change its height (data resolving, a tab filtering cards out, a display toggle syncing in from the Main Window).

The native side clamps the reported value to `[POPOVER_MIN_HEIGHT, POPOVER_MAX_HEIGHT]` (180-620 logical px) and grows the panel downwards from its anchor under the tray icon, so a resize never needs a reposition. When the clamp bites, the panel simply scrolls its card area internally — which is why `.popover-root` is `100vh` tall: it always fills whatever the panel ended up being, and the scroll area absorbs the difference.

The rest of the native half of the contract: `commands::set_popover_height` (in [src-tauri/src/commands/mod.rs](../../../src-tauri/src/commands/mod.rs)) validates the value and delegates to `popover_panel::set_height`, which resizes both the `NSPanel`'s own frame (`setFrame_display`, keeping the top-left anchor fixed) and the hosted `wry::WebView`'s bounds (`WebView::set_bounds`) to match — the panel and its webview are two separate native objects here (unlike a Tauri `WebviewWindow`, where resizing the window resizes its webview automatically), so both have to be resized explicitly.

- `height` is the desired **outer** height of the panel in logical pixels (CSS px), including its own top/bottom padding. Width is never passed and never changes.
- Out-of-range values are clamped, not rejected — an over-tall panel scrolls rather than running off the screen. `POPOVER_MAX_HEIGHT` (620) is deliberately small enough that the panel still fits below the menu bar on the shortest display Apple ships (1280×800), which is why no additional screen-height clamp is needed at positioning time.
- A non-finite `height` (`NaN`/`Infinity`) is rejected with an error and changes nothing.
- Calling it repeatedly is cheap and idempotent, and calling it while the panel is hidden is fine — in fact the normal case, since the frontend loads at startup and reports long before the user first clicks the tray icon.
- On a non-macOS build there is no Popover panel and the command is a silent no-op rather than an error.
- `POPOVER_DEFAULT_HEIGHT` (480) is only the height the panel is *created* with, before the frontend has reported anything.

`POPOVER_WIDTH`/`POPOVER_MIN_HEIGHT`/`POPOVER_MAX_HEIGHT`/`POPOVER_DEFAULT_HEIGHT`/`POPOVER_CORNER_RADIUS`/`POPOVER_MENU_BAR_GAP`/`POPOVER_SCREEN_MARGIN` all live in [src-tauri/src/windows.rs](../../../src-tauri/src/windows.rs), the single place this Popover geometry is defined for both `popover_panel.rs` (which builds and resizes the panel) and `commands` (which validates against the same bounds).

## Native Panel

The Popover is a genuine `NSPanel`, built directly in `create_panel` in [src-tauri/src/popover_panel.rs](../../../src-tauri/src/popover_panel.rs) via `objc2`/`objc2-app-kit` (`NSPanel::initWithContentRect_styleMask_backing_defer`), not through Tauri's `WebviewWindowBuilder` (which only ever constructs a plain `NSWindow` — see [History: the `WebviewWindow` attempt](#history-the-webviewwindow-attempt) for why that mattered).

- **Style mask and key status.** `NSWindowStyleMask::Borderless | NSWindowStyleMask::NonactivatingPanel` — the standard, Apple-documented style for menu-bar-anchored utility panels. A borderless panel does not become key by default, so `AILimitsPopoverPanel`, a narrow `NSPanel` subclass registered in `popover_panel.rs`, overrides only `canBecomeKeyWindow` to return `true`; this gives Escape an AppKit delivery path without activating AI Limits. `NonactivatingPanel` only has this effect on a window whose class actually inherits from `NSPanel`; this is why the previous plain-`NSWindow` attempt could not use it. Not independently verified on a real build in this environment — see [Status](#status).
- **Vibrancy/blur material.** `build_vibrancy_view` constructs an `NSVisualEffectView` (`.material = .menu`, `.blendingMode = .behindWindow`, `.state = .active`) as the panel's `contentView`, rather than reusing Tauri's `WindowEffectsConfig`/`window-vibrancy` wiring (not applicable here, since this window is never built through `WebviewWindowBuilder`). `Material::Menu` is the material the system's own menu-bar status-item dropdowns use (Wi-Fi, Bluetooth, Control Center); `.popover` was tried first but its tint reads visibly different since it is meant for a true arrow-tipped `NSPopover`, not an anchored menu-bar panel. For the vibrancy to show through, nothing in the webview paints an opaque background — `body.popover-page` is `transparent`, and the panel content is alpha overlays only, see [Visual Layer](#visual-layer). The `?showcase=popover` preview has no real vibrancy (it is not a native window), so its stage supplies a colored backdrop and a stand-in shadow; the panel content itself is styled identically in both places.
- **Corner radius.** The `NSVisualEffectView`'s `CALayer` gets `cornerRadius = POPOVER_CORNER_RADIUS`, `masksToBounds = true` and `cornerCurve = .continuous` (`objc2-quartz-core`'s `CALayer`), matching the `border-radius: 11px` the panel content uses — see [Visual Layer](#visual-layer). The two must stay equal or the content's own clipping will not sit on the window's curve. `cornerCurve` matters on its own: system panels round with the continuous ("squircle") curve, not a plain circular arc, and a circular corner at the same radius reads visibly tighter than the system's. The `WKWebView` child gets the identical `cornerRadius`/`masksToBounds`/`cornerCurve` applied to its own `CALayer` too (`create_webview`) — `WKWebView` composites its GPU-accelerated content through its own remote layer, which does not inherit `masksToBounds` from the `NSVisualEffectView` it was added as a subview of, so without this the webview's own square corners showed through at the panel's corners, under the rounded vibrancy.
- **Space membership.** `set_collection_behavior` sets `NSWindowCollectionBehavior::MoveToActiveSpace | IgnoresCycle | CanJoinAllApplications`. `CanJoinAllApplications` is the AppKit behavior specifically permitting a floating window to join other applications' fullscreen spaces; it must not be combined with `FullScreenAuxiliary`, because AppKit defines those fullscreen behaviors as mutually exclusive. `MoveToActiveSpace` moves the panel onto whichever single Space is active at the moment it is shown, rather than joining every Space persistently — see [Dismissal](#dismissal) for why this replaced `CanJoinAllSpaces`, and manually confirmed to fix the flicker described there. `IgnoresCycle` keeps the panel out of window cycling. Re-applied on every show (`show_near_tray`), not just once at construction. If the panel was shown while the Main Window was fullscreen, AppKit retains an auxiliary-space association after that window exits fullscreen; a native `NSWindowDidExitFullScreenNotification` observer hides the panel and clears then reapplies its collection behavior, detaching that stale association before the next tray click.
- **Window level.** `set_level` raises the panel to `NSPopUpMenuWindowLevel` (`101`), the level Apple's own docs name for transient, status-item-anchored popup UI — above `NSFloatingWindowLevel` (`3`), `NSMainMenuWindowLevel` (`24`) and `NSStatusWindowLevel` (`25`). Re-applied on every show, alongside `set_collection_behavior`.
- **Shadow.** `setHasShadow(true)` plus `invalidateShadow()` after every `makeKeyAndOrderFront:` call in `show_near_tray`/`set_height` — a transparent window's shadow is derived from its rendered alpha and AppKit caches that shape, so it needs invalidating whenever content or size changed while hidden (both happen here: the vibrancy mask is on the webview surface, and [Window Size](#window-size) resizes the panel between showings).
- **Showing.** `show_near_tray` calls `panel.makeKeyAndOrderFront(None)`. The `NonactivatingPanel` style permits the panel to become key without activating its owning application, so Escape has an AppKit route immediately while the frontmost app remains active. `hide()` calls `panel.orderOut(None)`.
- **Not in Cmd+Tab or the Window menu.** `NSWindowCollectionBehavior::IgnoresCycle`, set as part of `set_collection_behavior` above. Cmd+Tab switches *applications*, not windows — AI Limits itself still appears there, as any app with a Dock icon does; this flag only keeps the Popover out of the Window menu's window list and window-cycling.

## Positioning

`reposition_near_tray` (in `popover_panel.rs`) anchors the panel horizontally centered on the clicked tray icon, `POPOVER_MENU_BAR_GAP` (6pt) below it, and keeps it `POPOVER_SCREEN_MARGIN` (8pt) clear of the display's left, right and bottom edges — same contract the earlier `WebviewWindow` attempt's `position_popover_near_tray` established (right display via `monitor_for_tray_icon`, both horizontal edges clamped, a gap below the menu bar rather than flush against it).

The coordinate handling is the one genuinely new piece of math this module needed, because `NSPanel` positioning is not routed through Tauri's `Window::set_position` (which does this conversion internally for an ordinary `WebviewWindow`):

- `TrayIconEvent::Click`'s `rect` and `AppHandle::cursor_position()` are physical, top-left-origin screen coordinates — the same convention used throughout this file.
- `Monitor::position()`/`size()` (still available directly on `AppHandle`, independent of any particular window) are physical in the same sense.
- The panel's own frame is set via `NSWindow::setFrameTopLeftPoint`, which takes a point in AppKit's screen space: bottom-left-origin, y growing upward, anchored to the *primary* screen's frame. `flip_to_ns_y` converts a logical, top-left-origin y into that convention with `ns_y = primary_screen_height - logical_y` — the same formula tao itself uses internally when it hands a logical `set_position` to `NSWindow` for an ordinary Tauri window.

`monitor_for_tray_icon` finds the display the icon was actually clicked on (rather than always the primary display) by testing each monitor's own scale factor, same approach as the earlier attempt.

Not verified on a real display in this environment (no attached display here — see [Status](#status)); the formula is grounded in tao's own documented conversion, not exercised against a live multi-monitor setup.

## Dismissal

Three native, focus-independent mechanisms, all installed by `install_dismiss_monitors` in `popover_panel.rs` right after `show_near_tray` orders the panel to the front, and torn down by `remove_dismiss_monitors`, called from every hide path via `hide()` — the single funnel every way of hiding the Popover goes through, so the monitors are never left running against a hidden panel.

**Click outside the panel.** A matched pair of `NSEvent` monitors watches `.leftMouseDown`/`.rightMouseDown`: the global monitor receives events sent to other applications, while the local monitor receives events dispatched within AI Limits before their normal target. Both use the same panel-and-tray-rect test, so a menu-bar click is excluded in either event route; every other click outside the panel hides it. This pair is necessary because AppKit global monitors do not receive events sent to their own application, which was why a click in the Main Window did not dismiss the panel.

The tray-icon check exists to fix a real race: this global monitor sees the tray icon's own `mouseDown`, which fires *before* `mouseUp` — the event `TrayIconEvent::Click` (handled by the tray click handler in `main.rs`) fires on. Without excluding the tray icon's own rect here, clicking it a second time to close an open Popover would hide the panel on `mouseDown` first; the tray click handler's own toggle-off check (`popover_panel::is_visible()`) would then run on `mouseUp` against an already-hidden panel and reopen it instead of leaving it closed. `show_near_tray` now takes the `TrayIcon` handle for exactly this reason, passing it through to `install_dismiss_monitors`/`dismiss_on_outside_click`. This exclusion was missing in an earlier revision of this file (the outside-click check compared only against the panel's own frame), which reproduced exactly that bug; fixed by adding `point_is_inside_tray_icon`, ported from the equivalent check in the pre-`NSPanel` attempt.

**Escape.** A second local/global monitor pair watches `.keyDown` and checks virtual keycode 53 (`kVK_Escape`, layout-independent), calling `hide()` directly. The borderless panel's `canBecomeKeyWindow` override lets `makeKeyAndOrderFront:` establish the local AppKit route while retaining `NonactivatingPanel`; the global monitor retains dismissal when an external application receives the event.

**Leaving the Space.** `NSWorkspaceActiveSpaceDidChangeNotification`, observed via `NSWorkspace.sharedWorkspace.notificationCenter` (not the default `NSNotificationCenter` — Space changes are workspace-level, not per-app). A gesture-driven Space switch moves no keyboard focus at all (there is no window to lose focus from — the desktop just changes underneath it), so neither of the other two monitors would ever catch this case on its own. This observer fires on any active-Space change for any reason — gesture, Mission Control, Cmd+Left/Right, another app entering fullscreen — while installed, and unconditionally hides the panel. This keeps the panel closed after a swipe back to its original Space; it is no longer what makes the panel disappear from the *destination* Space of the swipe that opened this investigation — see the flicker note below.

**Space-switch flicker, fixed.** An earlier revision set `NSWindowCollectionBehavior::CanJoinAllSpaces`, which makes the window server genuinely render the panel on every Space at once. Swiping to a different Space while the panel was open then showed it briefly on the destination Space before the "Leaving the Space" observer above could hide it — that notification fires only after the Space-switch animation (and its first rendered frame) has already completed, so the app-side `hide()` always landed one frame late. Manually reproduced on a real device. Fixed by replacing `CanJoinAllSpaces` with `NSWindowCollectionBehavior::MoveToActiveSpace` in `set_collection_behavior` (see [Native Panel](#native-panel)): the panel now moves onto only the Space that is active when it is shown, rather than joining every Space persistently, so there is nothing for the window server to render on a Space the user swipes to afterward. Manually confirmed fixed on a real device for ordinary Space transitions; the Fullscreen-Space-of-another-app case (`CanJoinAllApplications`, kept unchanged) still needs its own confirmation — see [Open Items](#open-items).

The repeat-tray-click fix has not been separately exercised against a real display in this environment — see [Status](#status).

## History: the `WebviewWindow` attempt

Before the `NSPanel` implementation above, an earlier round built the Popover as an ordinary Tauri `WebviewWindow` (`install_popover_window` in `main.rs`, since removed) with `NSWindow` flags manually set to approximate panel-like behavior: `.transparent(true)` + `.effects(WindowEffectsConfig { effects: vec![Effect::Popover], .. })` for vibrancy (Tauri's own `window-vibrancy`-backed wiring), `set_collection_behavior` for `CanJoinAllSpaces`/`Stationary`/`IgnoresCycle`/`FullScreenAuxiliary`, `set_popover_window_level` raising `NSWindow.level` to `NSPopUpMenuWindowLevel`, and `order_front_without_activating` calling `-[NSWindow orderFrontRegardless]` directly to avoid the app-activation side effect of Tauri's `show()`/`set_focus()`.

That combination fixed two real, separately-diagnosed bugs across two rounds of manual testing — opening the Popover was forcibly switching the user's Space (fixed by `order_front_without_activating`), and the Popover was "leaking" onto other Spaces after a gesture-driven Space switch (fixed by the Space-change dismiss observer, carried forward unchanged into [Dismissal](#dismissal) above) — but did **not** fix the specific criterion the whole `NSPanel` investigation exists for: in a real manual check, when another app occupied a true Fullscreen Space, invoking the Popover did not show it on that Space; it became visible on a neighbouring ordinary Space instead. `NSWindow.level`/`collectionBehavior` on a plain `NSWindow` were not sufficient to fix this — the two ruled-out alternatives considered before moving to a real `NSPanel` were `object_setClass`-swapping the already-built `NSWindow` (rejected as unsupported and version-fragile, since tao already installs its own ivars/behavior on that instance) and runtime isa-swizzling `acceptsFirstMouse:` onto WKWebView's private view hierarchy (rejected as relying on Apple-internal, version-dependent implementation details). Both are recorded here as ruled out, not as something to revisit without a strong new reason.

## Menu Bar Icon

**Template image.** The tray icon is `icons/icon-tray.png`, a purpose-built macOS template image: monochrome, alpha-only, 18pt rendered at @2x (36×36 px), loaded with `TrayIconBuilder::icon(..)` + `.icon_as_template(true)`. `icon_as_template` sets `NSImage.isTemplate`, which is what makes AppKit tint the shape for the current menu bar appearance — light or dark, and inverted while the icon is highlighted — instead of blitting the pixels verbatim. The previous placeholder was the full-color app bundle icon (`app.default_window_icon()`), which is the single most obvious "this is not a native app" tell in the menu bar.

The artwork is the app's own four-point mark from `icons/icon-master.svg` with the per-arc brand colors stripped and one uniform stroke, generated by `scripts/generate-desktop-icons.sh` alongside the other icon assets: it writes `icons/icon-tray.svg` (24-unit viewBox rendered at 18pt, artwork scaled to 0.80 for optical margin, 2.35 stroke ≈ 1.4pt — the SF Symbols-like weight the menu bar expects) and rasterizes it through `scripts/render-svg-png.mjs`, a small Playwright/Chromium rasterizer. Playwright is already a devDependency for the showcase screenshots, and the Tauri CLI's own `tauri icon` cannot produce this (it only emits the full app-icon set). The master's fifth path — the doubled accent arc — is dropped, since it is invisible once the artwork is monochrome at menu bar size.

36×36 is the only size shipped: the tray API takes exactly one image and rescales it to an 18pt height, and macOS has no @3x displays. The PNG is `include_bytes!`-embedded in the binary rather than read from disk, so it ships inside the `.app` with no resource-path resolution and no missing-file failure mode; `bundle.icon` in tauri.conf.json is unrelated and unchanged. Loading it needs Tauri's `image-png` Cargo feature (added in `src-tauri/Cargo.toml`) for `Image::from_bytes`.

**Right-click menu.** `build_tray_menu` attaches a three-item context menu — "Open AI Limits", "Settings…", separator, "Quit" — shown on right click only (`show_menu_on_left_click(false)` keeps the left click as the Popover toggle). Its items carry the same menu ids the native app menu already uses, and `handle_menu_event` dispatches both by delegating to the existing `open_main_window` / `open_main_window_settings` / `open_main_window_help` commands, so each action has one implementation regardless of entry point. Quit is `PredefinedMenuItem::quit`, the same item the app menu carries.

Two side effects of that consolidation, both improvements: the app menu's own "Settings…" (Cmd+,) and Help items now *show and focus* the Main Window instead of only eval'ing into it — previously they did nothing visible if the Main Window had been closed to the tray — and they hide the Popover, as any navigation into the Main Window does.

## Signing

The Popover's `NSPanel` (see [Native Panel](#native-panel)) is built directly in-process, in the same executable as the Main Window — not as a separate native executable, helper app, or app extension (`.appex`).

Consequence: it does **not** require signing beyond the existing pipeline in [macos-signing.md](../../devops/macos-signing.md). The Developer ID signature, notarization, and stapling already cover the whole `.app` bundle, including every window/panel and the menu bar icon the same process presents. This is unlike a WidgetKit widget, which is a separate extension target requiring its own nested signature — the Popover has no such separate target.

If a later revision of this design introduces a genuinely separate helper process or extension for the Popover, this section must be revisited; as currently scoped (native UI inside the same app process), it does not apply.

## Local Testing

Same as the existing Main Window: local unsigned debug builds via `npm run tauri:build:debug` (see [local-build.md](../setup/local-build.md)) are sufficient to test the Popover during development. No additional signing or provisioning step is needed to test it locally, for the same reason given above — it is not a separate signed target.

Wrapping it in an actual `NSPopover` (or hand-drawing an arrow shape) is a bigger, separate task that has not been scoped or requested yet.
- **Panel appearance is unverified on a real macOS build.** The [Visual Layer](#visual-layer) was reviewed only through the `?showcase=popover` browser preview, which stands in for the vibrancy material with a flat colored backdrop. How the alpha overlays actually read over a live `NSVisualEffectMaterial::Popover` — tile contrast, hairline visibility, and whether the 11px CSS radius lines up exactly with the native panel's radius — still needs a look on a real build, in both themes and over both light and dark desktop content.
- **`localStorage` sharing between the Popover's webview and the Main Window's — unverified assumption.** See [Status](#status): the settings/theme cross-window sync depends on both webviews resolving to the same `WKWebsiteDataStore`-backed origin under `tauri://localhost`, which could not be checked in this environment.
